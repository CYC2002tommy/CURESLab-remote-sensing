# RAG 決策速查表

判斷用的，不是查定義用的。定義看 `glossary.md`，技術細節看 `patterns.md`。

---

## 該不該用 RAG

| 症狀 | 判斷 |
|---|---|
| 需要模型不知道的知識、知識會更新、有隱私要求、要降低幻覺 | **用 RAG** |
| 需要多步推理、數學計算、創造性生成 | **RAG 幫不上忙**——換模型或換方法 |
| 語料 < 一個 context window | **直接塞進去**，檢索只會減少資訊 |

## 風險分級 → 人工介入強度

| 風險 | 案例 | 要求 |
|---|---|---|
| 低 | 翻譯、語法檢查 | 可全自動 |
| 中 | 合約起草、法律諮詢 | **必須人工審核** |
| 高 | 證據分析、簽證決策 | **嚴格品質控制機制** |

## 分塊決策

| 條件 | 選擇 |
|---|---|
| 預設 / 不確定 | **遞迴字元分塊** |
| Markdown / HTML / LaTeX | **文檔結構分塊 → 再遞迴細分**（兩階段，小塊繼承標題元資料） |
| 主題混雜的長文 | 語義分塊（成本高） |
| 日誌、資料預處理 | 固定大小分塊 |
| 句間語義緊密（法律、醫療） | 語義分塊用 `gradient` 斷點法 |

**硬規則**
- 塊大小 **≤ 嵌入模型 Max Tokens**，但最適值**遠低於**上限
- 一個塊 = **一個主題**（不是「一個塊 = N 字元」）
- CJK 必須加分隔符 `。！？；`，長度用 **tokenizer 量**不是字元數
- 中文一字 ≈ 1–1.5 token，英文一字元 ≈ 0.25 token（**差 4–6 倍**）

**塊太大的三個獨立傷害**（發生在不同階段）
1. 索引期：池化資訊損失
2. 生成期：Lost in the Middle
3. 檢索期：主題稀釋 → **根本召不回來**

## 檢索策略選擇

| 查詢特徵 | 策略 |
|---|---|
| 專有名詞、型號、函式名 | 稀疏加權 |
| 同義詞、概念性提問 | 密集加權 |
| 兩者都有（多數情況） | **混合檢索 + RRF** |
| 複雜度 < 0.4 | 傳統混合檢索 |
| 複雜度 > 0.7 或關係密集度 > 0.7 | 圖 RAG |
| 0.4 ≤ 複雜度 ≤ 0.7 | 組合檢索 + Round-robin |

## 融合策略

| 情境 | 選擇 | 理由 |
|---|---|---|
| **預設** | **RRF, c = 60** | 尺度無關，異質分數不需正規化 |
| 需明確調控語義 vs 關鍵詞比例 | 加權線性 + α | 可解釋的旋鈕，但需歸一化且要調參 |
| 只想要多樣性、不想調參 | Round-robin 輪詢 | 公平調度，實作簡單 |

⚠️ **top-k 切片上做 min-max 歸一化不穩定**——某通道結果少時尤其明顯。這是選 RRF 的主因。

## 重排方法選擇

| 條件 | 選擇 |
|---|---|
| 融合多路召回 | **RRF**（零樣本，無需訓練） |
| Top-K 精排，能接受延遲 | **Cross-Encoder**（精度最高，N 次推理） |
| 要接近 Cross-Encoder 精度但需可預先計算 | **ColBERT**（後期交互 MaxSim） |
| 高價值語義理解，候選少 | RankLLM |

**成本梯度**：RRF（低）< ColBERT（中）< RankLLM（中）< Cross-Encoder（**高**）
**交互粒度**：無 → 概念級 → 句子級 → **Token 級**
**可預先計算文件向量**：只有 ColBERT 可以

⚠️ **重排只能改善已召回文件的順序。召不回來的，重排救不了。**

## 查詢處理選擇

| 症狀 | 技術 |
|---|---|
| 問題含多個子主題 | **Multi-query 分解** → 並行檢索 → 合併去重 |
| 問題太具體、直接答易錯 | **Step-Back Prompting**（先問原理再推導） |
| 查詢短、文件長，向量對不上 | **HyDE**（生成假設文件再嵌入；**不必事實正確**） |
| 「最短的」「最多的」排序/極值 | **LLM 生成 JSON 指令 + 程式碼執行**（向量檢索的盲區） |
| 多個資料源 | 查詢路由 |

⚠️ **`SelfQueryRetriever` 處理不了排序/比較查詢。**

## 路由方法

| 條件 | 選擇 |
|---|---|
| 需要靈活、複雜路由邏輯 | LLM 意圖識別 |
| 延遲敏感、路由簡單 | 嵌入相似性路由 |
| **任何情況** | **必須有規則基礎的降級路徑** |

## 壓縮器選擇（成本由低到高）

| 壓縮器 | 機制 | 成本 |
|---|---|---|
| `EmbeddingsFilter` | 相似度閾值過濾 | **低**（無 LLM） |
| `LLMChainFilter` | LLM 判斷整篇去留 | 中 |
| `LLMChainExtractor` | LLM 提取相關句 | 高 |

## 三段式職責分工

| 階段 | 解決 | 假設 |
|---|---|---|
| 重排 | 順序不對 | 召回集裡有答案 |
| 壓縮 | 塊裡有噪音 | 召回大體正確 |
| **校正 (C-RAG)** | **檢索本身失敗** | **不做假設** |

**C-RAG 三分支**：正確 → 知識精煉（拆 strips 濾噪音）｜不正確 → **查詢重寫 + Web 搜尋**｜模糊 → **原查詢 + Web 搜尋**

## 向量資料庫選型

| 條件 | 選擇 |
|---|---|
| 新手 / 小型專案 / 原型 | **ChromaDB 或 FAISS** |
| 資料量 > 百萬級 | Milvus / Weaviate / Pinecone |
| 需高並發、即時更新、複雜元資料過濾 | Milvus / Weaviate / Pinecone |
| 效能敏感、中小規模 | Qdrant |
| 完全不想維運 | Pinecone（99.95% SLA，<100ms） |
| **需要稀疏向量原生支援** | **Milvus**（`SPARSE_FLOAT_VECTOR`） |

**FAISS 的五個硬限制**：純函式庫、無持久化、單機、元資料弱、高並發受限

## 嵌入模型選型

| 檢查項 | 要求 |
|---|---|
| 任務排名 | 看 **Retrieval** 不是平均分 |
| 語言 | 中文 RAG 必須明確支援中文或多語言 |
| Max Tokens | **決定分塊上限** |
| 驗證方式 | **必須建私有評測集**，MTEB 只是篩選工具 |

**BGE-M3 = 多語言（100+）+ 多功能（dense/sparse/multi-vector 一次產出）+ 多粒度（8192 token）**

## 評估

| 分數低的維度 | 該修哪裡 |
|---|---|
| **上下文相關性** | 檢索（分塊、混合檢索、重排） |
| **忠實度** | 提示詞或換模型（幻覺問題） |
| **答案相關性** | 生成階段的完整性 |

**檢索指標全部需要 ground truth**：P@k、R@k、F1、MRR、MAP

| 指標 | 何時用 |
|---|---|
| Precision@k | 在意噪音少 |
| Recall@k | 在意沒漏掉 |
| MRR | 使用者只看第一個答案 |
| MAP | 綜合精確率與排名 |

| 詞彙重疊指標 | 導向 |
|---|---|
| ROUGE | 召回率——**說全了沒** |
| BLEU | 精確率 + 長度懲罰——**說對了沒** |
| METEOR | 綜合 + 同義詞匹配 |

**工具三段接力**：開發中 → **LlamaIndex Eval**｜版本回歸 → **RAGAS**｜生產監控 → **Phoenix**

⚠️ RAGAS 中 **`context_recall` 仍需 ground_truth**，不是所有指標都免標註。
⚠️ **LLM 裁判有評估者偏見**，數字當相對訊號用，不是絕對品質量測。

## 格式化生成（可靠性由低到高）

| 方法 | 控制點 |
|---|---|

| Output Parsers | 輸出端驗證 |

## 安全紅線

| 禁止 | 原因 | 替代 |
|---|---|---|
| 生產環境用 `PandasQueryEngine` | `eval()` 執行 LLM 生成的程式碼 | 摘要索引路由 + MetadataFilter 兩步查詢 |
| Neo4j 生產環境物理刪除 | 級聯破壞關係 | **軟刪除**（`SET is_active = false`） |
| 直接 `DELETE` 有關係的節點 | Neo4j 直接報錯 | `DETACH DELETE` |
| 用 `CREATE` 建構圖譜實體 | 產生重複節點 | `MERGE` + `ON CREATE/MATCH SET` |
| 直接執行 LLM 生成的 SQL | 注入風險 | 限唯讀 + 語法/權限驗證 |
