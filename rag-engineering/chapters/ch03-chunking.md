# Chapter 3: 文本分塊 — 四種策略與三個失敗機制

## Core Idea
分塊不是為了「切小一點好塞進去」，而是為了讓**每個塊聚焦單一主題**。塊切太大會透過三個獨立機制傷害系統，而這三個機制都不是「超出上下文窗口」——即使模型吃得下，大塊依然有害。

## Frameworks Introduced

- **「塊不是越大越好」的三個失敗機制**：這是本章最重要的內容，也是實務上最常被誤解的地方。
  - When to use: 有人問「嵌入模型能吃 8192 token，那我切 8000 好不好？」時。
  - How: 三個機制獨立作用，缺一不可地解釋為什麼要切小：

| 機制 | 發生在哪 | 原理 |
|---|---|---|
| **嵌入過程的資訊損失** | 索引時 | Transformer 池化（[CLS] 或 mean pooling）把所有 token 壓成單一向量。塊越長，語義點越多，這個向量承載的資訊越稀釋，表示變得籠統，關鍵細節被模糊 |
| **Lost in the Middle** | 生成時 | LLM 處理長上下文時傾向記住開頭與結尾，忽略中間。大塊塞滿噪音，關鍵資訊被「淹沒」 |
| **主題稀釋導致檢索失敗** | 檢索時 | 一個塊混雜多主題，整體語義被稀釋，相關性分數拉低，**根本召不回來** |

- **四種基礎分塊策略**：依文件結構選擇，不是依偏好。
  - When to use: 每個新語料來源都要做一次這個決策。
  - How: 見下方 Reference Tables。

- **兩階段分塊 (結構分塊 → 遞迴細分)**：處理結構化文件的理想方案。
  - When to use: Markdown、HTML、LaTeX 等有明確結構標記的文件。
  - How:
    1. 先用 `MarkdownHeaderTextSplitter` 按標題階層切成大的邏輯塊，**標題路徑自動存入元資料**。
    2. 再對這些邏輯塊套用 `RecursiveCharacterTextSplitter` 切到符合 `chunk_size`。
    3. 所有小塊**繼承第一步的標題元資料** → 既保留宏觀結構，又控制了塊大小。
  - Why it works: 元資料注入等於給每個塊一個精確的「地址」（如 `{"Header 1": "第三章：模型評估", "Header 2": "3.2節：評估指標"}`），讓模型理解片段的來源與背景。這也是結構化索引（ch06）的前置步驟。

## Key Concepts
- **chunk_size / chunk_overlap** — 塊大小與重疊。重疊用來維持塊間的上下文連續性。
- **主題稀釋 (Topic dilution)** — 單一塊包含多個不相關主題，導致整體相關性分數被拉低。
- **Lost in the Middle** — Liu et al. (2023) 的發現：LLM 對長上下文的中段記憶顯著較差。
- **語義斷點 (Breakpoint)** — 語義分塊中，相鄰句子嵌入距離超過閾值的位置。
- **段落感知的自適應分塊** — LangChain `CharacterTextSplitter` 的實際行為（並非嚴格固定大小）。

## Mental Models
- **塊大小的上限由嵌入模型決定，但最適值遠低於上限**：`bge-base-zh-v1.5` 的窗口是 512 token，這是硬限制；但即使模型能吃 8192，切 8000 依然是錯的。
- **「一個塊 = 一個主題」是判準，不是「一個塊 = N 個字元」**：切分的目標是主題聚焦，字元數只是實作手段。
- **分塊決定檢索的信噪比**：合理分塊提升信噪比，確保生成環節拿到最優質的上下文。
- **CJK 沒有詞邊界，預設分隔符會失效**：中文、日文、泰文必須在遞迴分隔符清單中加入 `。！？；` 這類全形標點，否則遞迴分塊在 `" "` 這一層完全切不動。

## Anti-patterns
- **把不同主題塞進同一個大塊**：書中的例子——把「技能介紹」「推薦出裝」「背景故事」放進一個巨大塊，查「怎麼出裝」時整塊分數低到召不回來。正確做法是切成三個主題聚焦的塊。
- **用字元數當中文的長度單位而不驗證 token 數**：中文一個字約 1–1.5 token，英文一個字元約 0.25 token。同樣的字元預算，中英文的實際 token 數差 4–6 倍。
- **固定大小分塊遇到超長段落就放棄**：`CharacterTextSplitter` 只會發警告然後保留超長塊。遞迴分塊才會繼續用更細的分隔符處理。
- **只按標題切、不做細分**：某章節內容可能遠超上下文窗口。必須組合遞迴分塊。

## Reference Tables

### 四種基礎分塊策略對比
| 策略 | 原理 | 優勢 | 劣勢 | 適用 |
|---|---|---|---|---|
| **固定大小分塊** | 按 `\n\n` 分段，累積合併到 `chunk_size` | 實作簡單、速度快、開銷小 | 可能在語義邊界切斷 | 日誌分析、資料預處理 |
| **遞迴字元分塊** | 分隔符階層遞迴：段落→句子→詞→字元 | 平衡語義完整性與大小控制；超長段落能繼續切 | 仍不理解語義 | **通用預設選擇** |
| **語義分塊** | 計算相鄰句子嵌入距離，在語義跳躍處切 | 塊內語義高度一致 | 需額外嵌入計算，成本高 | 主題混雜的長文 |
| **文檔結構分塊** | 依 Markdown/HTML/LaTeX 標記切 | 保留結構語義，自動產生元資料 | 僅適用結構化文件；需組合細分 | **結構化文件的首選** |

### 語義分塊的四種斷點判定法
| 方法 | 邏輯 | 預設參數 | 適用 |
|---|---|---|---|
| `percentile`（預設） | 差異值超過第 N 百分位即為斷點 | 95（只取最顯著的 5%） | 一般文本 |
| `standard_deviation` | 差異值 > 平均 + N×標準差 | 3 | 差異分布近常態時 |
| `interquartile` | 差異值 > Q3 + N×IQR | 1.5 | 有離群值時較穩健 |
| `gradient` | 先算差異的變化率，再對梯度套百分位 | 95 | **句間語義緊密、差異普遍低的文本**（法律、醫療） |

### 其他框架的分塊能力
| 框架 | 機制 | 特點 |
|---|---|---|
| **Unstructured** | 先分區 (Partitioning) 成帶語義標籤的元素，再分塊 | `basic` 填滿至上限；`by_title` 遇 Title 元素強制開新塊。「先理解、後分割」，適用範圍比 Markdown splitter 廣 |
| **LlamaIndex** | 節點解析器 (Node Parser) | 結構感知型（Markdown/JSON/Code）、語義感知型（`SemanticSplitterNodeParser`、`SentenceWindowNodeParser`）、常規型（Token/Sentence） |
| **ChunkViz** | 視覺化工具 | 用顏色塊展示 chunk 邊界與重疊，快速理解分塊邏輯 |

## Worked Example
**「鲁班七号攻略」——書中用來說明主題稀釋的例子。**

文件內容：一份遊戲英雄攻略，含「技能介紹」「推薦出裝」「背景故事」三部分。

**糟糕的分塊**：三部分全部放進一個巨大塊。
- 玩家查詢「鲁班七号怎么出装？」
- 這個塊**確實包含**出裝資訊
- 但整塊的語義被技能說明與英雄故事嚴重稀釋
- 整體相關性分數偏低 → **無法被召回**
- 結果：資訊明明在庫裡，系統卻答不出來

**優秀的分塊**：切成「技能」「出裝」「故事」三個獨立的主題聚焦塊。
- 同樣查詢
- 「推薦出裝」這個塊與查詢高度相關 → 極高分數 → 精準召回

**這個例子的關鍵**：失敗不是因為塊「超出模型限制」，而是因為**塊的向量表示被稀釋了**。這就是為什麼三個失敗機制要分開理解——這個案例是純粹的檢索期失敗，跟 LLM 上下文窗口毫無關係。

## Key Takeaways
1. 「塊不是越大越好」有**三個獨立機制**：嵌入池化資訊損失（索引期）、Lost in the Middle（生成期）、主題稀釋（檢索期）。三者發生在不同階段。
2. **一個好的塊聚焦單一明確的主題**——這是判準，字元數只是手段。
3. 塊大小**必須 ≤ 嵌入模型的上下文窗口**（如 512 token），但最適值遠低於上限。
4. 結構化文件用**兩階段分塊**：標題切分（產生元資料）→ 遞迴細分（控制大小），小塊繼承標題元資料。
5. CJK 必須自訂分隔符加入 `。！？；`，且長度要用 tokenizer 量而非字元數。
6. 遞迴字元分塊是通用預設；語義分塊成本高但塊內一致性最好。
