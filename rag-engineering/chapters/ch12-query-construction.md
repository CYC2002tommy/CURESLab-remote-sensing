# Chapter 12: 查詢建構 — Metadata Filter / Cypher / Text-to-SQL

## Core Idea
向量檢索處理不了「2023 年 Q2 的財報中關於 AI 的論述」這種**混合了結構化條件與語義查詢**的問題。查詢建構的職責是把自然語言翻譯成目標資料源的**原生查詢語言**——元資料過濾器、Cypher 或 SQL。

## Frameworks Introduced

- **三種查詢建構目標**：依資料源類型選擇。

| 資料源 | 目標語言 | 技術 |
|---|---|---|
| 向量資料庫（含元資料） | 元資料過濾器 | **Text-to-metadata-filter**（`SelfQueryRetriever`） |
| 圖資料庫 | Cypher | **Text-to-Cypher** |
| 關聯式資料庫 | SQL | **Text-to-SQL** |

- **Text-to-SQL 的三大業務挑戰**：
  1. **「幻覺」問題** — LLM 可能「想像」出資料庫中不存在的表或欄位，導致 SQL 無效
  2. **對資料庫結構理解不足** — 需準確理解表結構、欄位含義、表間關聯，才能生成正確的 `JOIN` 與 `WHERE`
  3. **處理使用者輸入的模糊性** — 提問可能有拼寫錯誤或不規範表達（如「上個月的銷售冠軍是誰？」），模型需要容錯與推理能力

- **Text-to-SQL 三層優化策略**（由基礎到進階）：
  1. **提供精確的資料庫模式** — 向 LLM 提供相關表的 `CREATE TABLE` 語句。**這是最基礎也最關鍵的一步**，等於給了 LLM 一張地圖（表名、欄位名、資料型別、外鍵關係）。
  2. **提供少量高品質示例** — 在提示中加入「問題-SQL」示例對，可極大提升準確性。
  3. **利用 RAG 增強上下文** — 為資料庫建構專門的「知識庫」，其中不僅包含表的 DDL，還可包含：
     - **表和欄位的詳細描述** — 用自然語言解釋每個表做什麼、每個欄位代表什麼業務含義
     - **同義詞和業務術語** — 例如將使用者的「花費」映射到資料庫的 `cost` 欄位
     - **複雜的查詢示例** — 提供含 `JOIN`、`GROUP BY` 或子查詢的複雜問答對

     使用者提問時，系統先從這個知識庫檢索最相關的資訊（相關表結構、欄位描述、相似查詢），再生成 SQL。

## Key Concepts
- **`SelfQueryRetriever`** — LangChain 的自查詢檢索器，能從自然語言中抽出元資料過濾條件。**已知限制：無法正確處理需要排序或比較的查詢**（如「時間最短的影片」）。
- **DDL (Data Definition Language)** — `CREATE TABLE` 這類定義資料結構的語句。
- **Cypher** — Neo4j 的宣告式圖查詢語言，語法靈感來自 SQL 但針對圖特性優化。

## Mental Models
- **查詢建構是「翻譯」不是「檢索」**：它的產出是一段可執行的查詢語句，執行由資料源負責。
- **給 LLM 地圖，不要讓它猜**：Text-to-SQL 的幻覺幾乎全來自模式資訊不足。提供完整 DDL 是投報率最高的一步。
- **RAG 可以用來增強 RAG**：為資料庫模式本身建一個知識庫，這是「用 RAG 解決 Text-to-SQL 的模式理解問題」——遞迴地應用了同一套技術。
- **業務術語映射是隱形的關鍵**：使用者說「花費」，資料庫欄位叫 `cost`。沒有這層映射，語義再強的模型也對不上。

## Anti-patterns
- **用 `SelfQueryRetriever` 處理排序/極值查詢**：書中明確指出它處理不了「時間最短的影片」。應改用「LLM 生成 JSON 排序指令 + 程式碼執行」（見 ch10 提示工程）。
- **只給表名不給 DDL**：LLM 會猜欄位名，產生無效 SQL。
- **忽略業務術語與資料庫欄位的落差**：使用者的詞彙與 schema 的詞彙幾乎不會一致。
- **直接執行 LLM 生成的 SQL 而不做防護**：與 ch06 的 `PandasQueryEngine` 同類風險。生成的查詢應限制為唯讀，並做語法/權限驗證。

## Reference Tables

### 三種查詢建構的對照
| | Text-to-metadata-filter | Text-to-Cypher | Text-to-SQL |
|---|---|---|---|
| 目標 | 向量庫的元資料過濾條件 | 圖遍歷查詢 | 關聯式查詢 |
| 典型用途 | 「2023 年的財報」→ `year == 2023` | 「A 公司和 B 公司的投資關係」 | 「我上次訂購了什麼？」 |
| 主要風險 | 排序/比較查詢處理不了 | 圖模式理解錯誤 | 幻覺出不存在的表/欄位 |
| 關鍵輸入 | 元資料 schema | 節點標籤與關係類型 | `CREATE TABLE` DDL |

### Text-to-SQL 優化策略的投報率
| 策略 | 成本 | 效果 | 順序 |
|---|---|---|---|
| 提供 `CREATE TABLE` DDL | 低 | **高** | **先做這個** |
| 提供 few-shot「問題-SQL」示例 | 低 | 高 | 再做這個 |
| RAG 增強（DDL + 欄位描述 + 術語映射 + 複雜示例） | 中 | 高 | 前兩者不夠時 |

## Worked Example
**「請總結一下 2023 年第二季財報中關於 AI 的論述」**——這個查詢為什麼需要查詢建構。

**純向量檢索的失敗**：把整句話丟去做語義相似度搜尋。
- 「2023 年」「第二季」這些條件在向量空間中**幾乎沒有區辨力**——所有財報的向量都很像
- 可能召回 2022 年 Q3 的 AI 論述，因為它語義上同樣接近
- **結構化條件被語義相似度稀釋了**

**查詢建構 + 結構化索引的解法**（兩階段）：
1. **查詢建構**：LLM 從自然語言中抽出結構化條件
   - `document_type == '財報'`
   - `year == 2023`
   - `quarter == 'Q2'`
   - 剩餘語義查詢：「關於 AI 的論述」
2. **元資料預過濾**：先用上述條件把候選集從全庫縮到該季財報
3. **向量搜尋**：在這個小得多的集合中，搜尋「關於 AI 的論述」

**關鍵洞見**：查詢中的**結構化部分**與**語義部分**應該用不同的機制處理。硬塞給向量檢索，結構化條件會被稀釋掉。

**銜接**：這個「先過濾，再搜尋」正是 ch06 結構化索引的執行流程；而元資料能被過濾的前提，是 ch03 分塊時就注入了這些欄位。

## Key Takeaways
1. 查詢建構把自然語言翻譯成**目標資料源的原生查詢語言**：元資料過濾器 / Cypher / SQL。
2. **結構化條件與語義查詢應分開處理** — 硬塞給向量檢索會讓結構化條件被稀釋。
3. **Text-to-SQL 三大挑戰**：幻覺（想像不存在的表/欄位）、模式理解不足（JOIN/WHERE 錯誤）、輸入模糊性。
4. **提供 `CREATE TABLE` DDL 是投報率最高的一步** — LLM 的幻覺幾乎全來自模式資訊不足。
5. **RAG 可用來增強 Text-to-SQL**：為資料庫建知識庫，包含 DDL、欄位業務描述、**同義詞與業務術語映射**（「花費」→ `cost`）、複雜查詢示例。
6. **`SelfQueryRetriever` 處理不了排序/比較查詢** — 改用 LLM 生成 JSON 指令的方案。
