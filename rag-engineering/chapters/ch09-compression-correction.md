# Chapter 9: 壓縮與校正 — 去噪與 C-RAG 自我修正

## Core Idea
重排解決「順序對不對」，壓縮解決「塊裡有多少廢話」，校正解決「檢索根本失敗了怎麼辦」。三者構成檢索進階的完整鏈路，而**校正是唯一質疑「檢索結果一定可信」這個隱含假設的環節**。

## Frameworks Introduced

- **壓縮 (Compression)** — 對召回內容去噪提煉。
  - When to use: 初步檢索到的塊整體相關，但包含大量無關的「噪音」文字時。
  - How: 兩種主要方式：
    1. **內容提取** — 從文件中只抽出與查詢相關的句子或段落
    2. **文件過濾** — 完全丟棄那些初步召回但精細判斷後認為不相關的整個文件
  - Why it matters: 未經處理的冗長上下文會（a）增加 API 成本與延遲，（b）因**資訊過載降低生成品質**——這正是 Lost in the Middle（ch03）的觸發條件。

- **C-RAG (Corrective-RAG) 校正檢索** — Jiang, Z. et al. (2024)。
  - When to use: 檢索系統可能回傳不相關、過時甚至完全錯誤的文件時（即：所有真實系統）。
  - How: **「檢索 → 評估 → 行動」**三階段：
    1. **檢索 (Retrieve)** — 與標準 RAG 相同
    2. **評估 (Assess)** — **關鍵步驟**。一個「檢索評估器 (Retrieval Evaluator)」判斷每個文件與查詢的相關性，給出三種標籤之一：**正確 (Correct) / 不正確 (Incorrect) / 模糊 (Ambiguous)**
    3. **行動 (Act)** — 依評估結果進入不同流程：

| 評估標籤 | 行動 | 細節 |
|---|---|---|
| **正確** | **知識精煉 (Knowledge Refinement)** | 將原始文件分解成更小的知識片段 (strips)，過濾掉無關部分，重新組合成更精準聚焦的上下文 |
| **不正確** | **知識搜尋 (Knowledge Searching)** | 認定內部知識庫無法回答。先做**查詢重寫 (Query Rewriting)** 生成更適合搜尋引擎的查詢，然後進行 **Web 搜尋**，用外部資訊回答 |
| **模糊** | **知識搜尋** | 同樣觸發，但通常**直接使用原始查詢**做 Web 搜尋，獲取額外資訊輔助生成 |

  - Why it works: 傳統 RAG 有個隱含假設——**檢索到的文件總是相關且包含正確答案**。C-RAG 打破這個假設，增加了一個「事實核查」層。系統不再盲目信任檢索結果，能在檢索失敗時主動尋求外部幫助。
  - 實作：LangChain 的 **`langgraph`** 庫，利用圖結構建構這種帶條件判斷與循環的複雜流程。

## Key Concepts
- **知識片段 (Strips)** — C-RAG 知識精煉階段把文件分解成的更小單位。
- **檢索評估器 (Retrieval Evaluator)** — C-RAG 的核心組件，本質上是把「上下文相關性」評估（ch14）搬進了執行時的推理迴路。
- **`ContextualCompressionRetriever`** — LangChain 的包裝器，包在基礎檢索器外。
- **`DocumentCompressor`** — 壓縮器的抽象介面。

## Mental Models
- **壓縮是在爭奪上下文的信噪比**：LLM 的上下文窗口是有限資源，塞進去的每個 token 都在跟其他 token 競爭注意力。壓縮是主動放棄低價值 token。
- **C-RAG 把評估從離線搬到線上**：ch14 的評估是開發時的診斷工具；C-RAG 的檢索評估器是**執行時**的守門員。同一個概念，兩種部署位置。
- **「檢索一定成功」是最危險的隱含假設**：現實中檢索會失敗。沒有校正層的系統，失敗時會把「有毒」的上下文直接餵給 LLM，導致幻覺。
- **成本梯度：EmbeddingsFilter < LLMChainFilter < LLMChainExtractor**：過濾比提取便宜，嵌入比 LLM 便宜。依預算選擇。

## Anti-patterns
- **把未經處理的長上下文直接餵給 LLM**：增加成本與延遲，且觸發資訊過載，降低答案品質。
- **盲目信任檢索結果**：這是 C-RAG 要解決的根本問題。檢索系統會失敗。
- **只做壓縮不做校正**：壓縮假設「召回的東西大體是對的，只是有雜訊」。當召回的東西**根本就是錯的**時，壓縮只會產出更精煉的錯誤。
- **用 LLM 壓縮每一個召回文件**：成本會失控。先用 `EmbeddingsFilter` 這類廉價方法粗篩。

## Reference Tables

### LangChain 內建的 DocumentCompressor
| 壓縮器 | 類型 | 機制 | 成本 |
|---|---|---|---|
| **`LLMChainExtractor`** | 內容提取 | 遍歷每個文件，用 LLM Chain 判斷並**提取出與查詢相關的部分** | 高（每文件一次 LLM 呼叫） |
| **`LLMChainFilter`** | 文件過濾 | 用 LLM 判斷**整個文件**是否相關；相關則保留全文，不相關則丟棄 | 中 |
| **`EmbeddingsFilter`** | 文件過濾 | 計算查詢與各文件嵌入的相似度，**只保留超過閾值**的文件 | **低**（無 LLM 呼叫） |

### LlamaIndex 的壓縮方案
| 組件 | 機制 |
|---|---|
| **`SentenceEmbeddingOptimizer`** | 後處理器（Node Postprocessor）。將每個檢索到的文件**分解成句子**，計算每個句子與查詢的嵌入相似度，**只保留相似度最高的句子** |

### 檢索進階三段式的職責分工
| 階段 | 解決什麼 | 假設 |
|---|---|---|
| **重排 (ch08)** | 順序不對——最相關的沒排在最前面 | 召回集裡有正確答案 |
| **壓縮 (本章)** | 塊裡有噪音——相關塊中混雜無關文字 | 召回的塊大體正確 |
| **校正 (本章)** | **檢索本身失敗了** | **不做任何假設** |

## Worked Example
**C-RAG 的三條分支如何改變系統行為。**

情境：使用者問「我們公司 2026 年的碳費申報截止日是哪天？」

**傳統 RAG**：檢索 → 召回 5 個塊 → 全部塞給 LLM → 生成答案。
- 若知識庫裡根本沒有 2026 年的規定（只有 2025 年的），召回的會是 2025 年的塊
- LLM 看到「截止日 3 月 31 日」，照著答
- **結果：自信地給出過時的錯誤答案**，且無從察覺

**C-RAG**：
1. **檢索** — 同樣召回 5 個塊
2. **評估** — 檢索評估器逐一判斷：這些塊講的是 2025 年，查詢問的是 2026 年 → 標記為 **Incorrect**
3. **行動** — 觸發知識搜尋分支：
   - **查詢重寫**：把「我們公司 2026 年的碳費申報截止日」改寫成更適合搜尋引擎的形式，如「2026 碳費 申報 期限 環境部」
   - **Web 搜尋**：取得外部即時資訊
   - 用外部資訊生成答案，並可標註來源為外部而非內部知識庫

**若評估結果是 Correct**：進入知識精煉——把召回的長文件拆成 strips，濾掉「碳費制度沿革」這類無關段落，只留下截止日相關的片段，組成更聚焦的上下文。

**若評估結果是 Ambiguous**：同樣做 Web 搜尋，但**直接用原始查詢**（不重寫），因為模糊意味著系統不確定該往哪個方向改寫。

**這個例子的關鍵**：傳統 RAG 與 C-RAG 的差別不在檢索品質，而在**系統是否知道自己失敗了**。

## Key Takeaways
1. **檢索進階三段式**：重排（順序）→ 壓縮（去噪）→ 校正（失敗處理）。三者假設層層放寬。
2. **壓縮有兩種**：內容提取（抽相關句）與文件過濾（整篇丟棄）。成本梯度為 `EmbeddingsFilter` < `LLMChainFilter` < `LLMChainExtractor`。
3. **C-RAG = 檢索 → 評估 → 行動**，評估器輸出**正確 / 不正確 / 模糊**三種標籤。
4. **正確 → 知識精煉**（拆 strips 濾噪音重組）；**不正確 → 查詢重寫 + Web 搜尋**；**模糊 → 直接用原查詢做 Web 搜尋**。
5. C-RAG 打破的隱含假設是「**檢索到的文件總是相關且包含正確答案**」。
6. 用 **`langgraph`** 建構這種帶條件判斷與循環的流程。
