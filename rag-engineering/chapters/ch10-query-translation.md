# Chapter 10: 查詢翻譯 — 提示工程 / Multi-query / Step-Back / HyDE

## Core Idea
使用者的原始問題**往往不是最優的檢索輸入**——它可能過於複雜、包含歧義，或與文件的實際措辭存在偏差。查詢翻譯的目標是彌合「使用者提問」與「文件儲存方式」之間的語義鴻溝，在檢索**之前**動手。

## Frameworks Introduced

- **提示工程重寫 (Prompt-engineered rewriting)**：讓 LLM 產生**可執行指令**而非改寫文字。
  - When to use: 查詢涉及排序、比較、極值（「時間最短的影片」）——這類查詢向量檢索本質上處理不了。
  - How:
    1. 設計提示詞，要求 LLM 輸出**結構化 JSON 指令**（而非改寫後的查詢）
    2. 程式碼解析 JSON 並執行對應操作
  - Why it works: 把 LLM 從「文字改寫員」提升為「能理解複雜意圖並生成可執行計畫的智能代理」。
  - 範例映射：
    - 「時間最短的影片」→ `{"sort_by": "length", "order": "asc"}`
    - 「播放量最高的影片」→ `{"sort_by": "view_count", "order": "desc"}`

- **多查詢分解 (Multi-query decomposition)**：把複合問題拆成原子子問題。
  - When to use: 問題包含多個子主題或意圖時。
  - How:
    1. LLM 從不同角度將原始問題分解成多個更簡單、更具體的子問題
    2. **並行**為每個子問題檢索
    3. 所有結果**合併、去重**，形成更全面的上下文
    4. 交給 LLM 生成最終答案
  - 實作：LangChain `MultiQueryRetriever`
  - Why it works: 複合問題的向量落在多個主題的「中間地帶」，可能哪個主題都不夠近。拆開後每個子查詢都能精準命中。

- **退步提示 (Step-Back Prompting)**：先問原理，再答細節。由 Google DeepMind 提出。
  - When to use: 問題細節繁多或過於具體，直接作答（即使用思維鏈）容易出錯時。
  - How:
    1. **抽象化**：引導 LLM 從原始具體問題生成一個更高層次、更概括的「退步問題」，探尋背後的通用原理或核心概念
    2. **推理**：先獲取退步問題的答案（一個物理定律、一段歷史背景），將這個通用原理作為上下文，再結合原始具體問題進行推理
  - Why it works: 先建立堅實的邏輯基礎，再往下推導，避免直接跳到細節時出錯。

- **HyDE (Hypothetical Document Embeddings)**：把「查詢→文件」匹配轉成「文件→文件」匹配。
  - When to use: 查詢簡短、關鍵詞有限，而庫中文件內容詳實、上下文豐富——兩者在向量空間存在鴻溝時。
  - How:
    1. **生成**：LLM 根據查詢生成一個**詳細的、可能是理想答案的假設性文件**。這個文件**不必符合事實**，但必須在語義上與一個好答案高度相關。
    2. **編碼**：將假設性文件輸入對比編碼器（如 Contriever），轉為向量。這個向量代表「理想答案」在語義空間中的位置。
    3. **檢索**：用這個向量在資料庫中做相似性搜尋。
  - Why it works: 把困難的「短查詢 → 長文件」匹配問題，轉化為相對容易的「長文件 → 長文件」匹配問題。
  - 出處：Gao, L. et al. (2022). *Precise Zero-Shot Dense Retrieval without Relevance Labels*.

## Key Concepts
- **語義鴻溝 (Semantic gap)** — 使用者自然語言提問與文件庫中儲存資訊之間的表述差異。
- **查詢翻譯 vs 查詢路由** — 翻譯是**改寫查詢本身**；路由是**選擇送去哪裡**（見 ch11）。兩者合稱「查詢重構與分發」。
- **假設性文件** — HyDE 生成的、不必真實但語義正確的答案樣本。

## Mental Models
- **不要直接拿使用者的話去檢索**：使用者的措辭與文件的措辭幾乎不會一致。查詢翻譯是在承認這個現實。
- **分解 → 並行檢索 → 合併去重**是處理複合問題的通用模式：一個查詢問多件事時，向量會落在主題間的空白地帶。
- **HyDE 的反直覺之處在於「假的文件比真的查詢更好用」**：因為向量空間中，文件與文件的距離比查詢與文件的距離更可靠。
- **極值/排序查詢是向量檢索的盲區**：「最短的」「最多的」這類需要全域比較的查詢，語義相似度根本不編碼這個資訊。必須轉成結構化指令（見 ch12 查詢建構）。

## Anti-patterns
- **用 SelfQueryRetriever 處理排序/比較查詢**：書中明確指出它無法正確處理「時間最短的影片」這類需要排序或比較的查詢。要改用「LLM 生成 JSON 指令 + 程式碼執行排序」的方案。
- **分解後不去重**：多個子查詢會召回重疊文件，不去重會浪費上下文預算，且可能觸發 Lost in the Middle。
- **要求 HyDE 生成的假設文件必須事實正確**：這誤解了 HyDE。假設文件只需**語義上像一個好答案**，事實錯誤不影響檢索效果。
- **所有查詢都套用全部四種技術**：每種都有 LLM 呼叫成本。應依查詢類型選用（這正是查詢路由要解決的問題）。

## Reference Tables

### 四種查詢翻譯技術選擇
| 技術 | 解決的問題 | LLM 呼叫次數 | 輸出 |
|---|---|---|---|
| **提示工程（JSON 指令）** | 排序、比較、極值查詢 | 1 | 結構化操作指令 |
| **Multi-query 分解** | 複合問題含多個子主題 | 1（分解）+ N（檢索不需 LLM） | N 個子查詢 |
| **Step-Back** | 問題過於具體，需先建立原理基礎 | 2（生成退步問題 + 最終推理） | 高層問題 + 最終答案 |
| **HyDE** | 短查詢 vs 長文件的向量鴻溝 | 1 | 假設性文件（再拿去嵌入） |

## Worked Example
**Multi-query 分解**——書中的範例：

原始問題：「在《流浪地球》中，劉慈欣對人工智慧和未來社會結構有何看法？」

這個問題實際上問了三件事，直接檢索會落在三個主題的中間地帶。

分解後的子問題：
1. 「《流浪地球》中描述的人工智慧技術有哪些？」
2. 「《流浪地球》中描繪的未來社會是怎樣的？」
3. 「劉慈欣關於人工智慧的觀點是什麼？」

系統對每個子問題**並行檢索**，然後**合併去重**，形成一個比原始查詢豐富得多的上下文。

---

**Step-Back Prompting**——書中的範例：

原始問題：「如果理想氣體的溫度增加 2 倍，體積增加 8 倍，其壓力會如何變化？」

直接算容易出錯（即使用思維鏈）。

- **退步問題**：「這個問題背後的物理原理是什麼？」
- **推理過程**：先回答退步問題，得到「理想氣體定律 $PV = nRT$」。然後基於這個定律代入具體數值計算，得出壓力變為原來的 1/4。

**關鍵**：先確立原理再代入數字，比直接操作數字穩健得多。

## Key Takeaways
1. **使用者的原始問題不是最優的檢索輸入**——查詢翻譯是在承認並修正這個現實。
2. **排序/比較/極值查詢是向量檢索的盲區**，必須轉成結構化指令由程式碼執行，不能靠語義相似度。
3. **Multi-query = 分解 → 並行檢索 → 合併去重**。複合問題的向量會落在主題間空白處。
4. **Step-Back = 先抽象出原理，再用原理推導細節**。適合細節繁多、直接作答易錯的問題。
5. **HyDE 生成的假設文件不必事實正確**，只需語義上像一個好答案。它把「查詢→文件」轉成「文件→文件」匹配。
6. 每種技術都有 LLM 成本，應依查詢類型選用——這就是查詢路由存在的理由。
