# Chapter 5: 向量資料庫 — 選型與 ANN 索引

## Core Idea
向量資料庫解決的是一個規模問題：當向量從幾百個增長到數百萬甚至數十億時，**暴力線性相似度計算的成本與延遲無法接受**。它與傳統資料庫是**互補而非替代**關係。

## Frameworks Introduced

- **向量資料庫的四層架構**：
  1. **儲存層** — 儲存向量與元資料，優化儲存效率，支援分散式
  2. **索引層** — 維護索引算法（HNSW、LSH、PQ 等），建立與優化索引
  3. **查詢層** — 處理查詢請求，支援混合查詢，實現查詢優化
  4. **服務層** — 管理客戶端連線，提供監控與日誌，實現安全管理

- **四類 ANN 索引技術**：
  - When to use: 理解不同向量庫的效能差異來源。
  - How:

| 類別 | 代表 | 原理 |
|---|---|---|
| **基於樹** | Annoy | 隨機投影樹，樹形結構實現對數複雜度搜尋 |
| **基於雜湊** | LSH（局部敏感雜湊） | 雜湊函數將相似向量映射到同一「桶」 |
| **基於圖** | **HNSW**（分層可導航小世界圖） | 多層鄰近圖結構實現快速搜尋 |
| **基於量化** | FAISS 的 **IVF**、**PQ** | 透過聚類與量化壓縮向量 |

- **FAISS → Milvus 的遷移論證**：書中明確列出的決策依據。
  - When to use: 從原型走向生產時的關鍵判斷。
  - How:

| FAISS 的局限 | Milvus 的優勢 |
|---|---|
| **純函式庫模式**：是向量搜尋庫，缺乏資料庫的完整功能 | **完整資料庫功能**：CRUD、事務支援、資料一致性保證 |
| **無持久化**：需手動管理資料持久化與備份 | **雲原生架構**：分散式部署、自動擴縮容、高可用 |
| **單機限制**：難以分散式部署與水平擴展 | — |
| **元資料支援有限**：無法高效儲存與查詢複雜的結構化元資料 | **豐富的元資料支援**：複雜 Schema 設計 |
| **並發效能**：高並發場景下受限 | **生產級特性**：監控、日誌、備份恢復 |

## Key Concepts
- **ANN (Approximate Nearest Neighbor)** — 近似最近鄰查詢。用精度換速度，在數十億級向量中實現毫秒級查詢。
- **最終一致性 vs 強一致性** — 向量資料庫通常為最終一致性；傳統 RDBMS 為強一致性（ACID 事務）。
- **標量過濾 (Scalar filtering)** — 相似性搜尋的同時按元資料欄位過濾（如「年份 > 2023」）。這是結構化索引（ch06）的基礎能力。

## Mental Models
- **向量庫與傳統資料庫互補**：實務上兩者並用——傳統資料庫存業務元資料與結構化資訊，向量資料庫專責處理 AI 模型產生的海量向量。
- **選型的分水嶺是「百萬級」與「並發需求」**：資料量超過百萬級，或需要高並發、即時更新、複雜元資料過濾時，才需要專業方案。
- **FAISS 是函式庫不是服務**：它把索引直接存成本地檔案（`.faiss` 索引檔 + `.pkl` 映射檔），而非執行一個資料庫服務。輕量高效，但也因此缺少所有資料庫特性。
- **索引是為了避開暴力搜尋**：所有 ANN 技術的本質都是「不要跟每個向量都比一次」。

## Anti-patterns
- **原型階段就上 Milvus 分散式部署**：新手/小型專案從 ChromaDB 或 FAISS 開始才是最佳選擇——與 LangChain/LlamaIndex 緊密整合，幾行程式碼就能跑。
- **生產環境用 FAISS 卻期待資料庫行為**：無持久化、無事務、單機、元資料弱。這五點是硬限制。
- **忽略元資料過濾需求就選型**：如果檢索流程需要「先過濾後搜尋」（ch06 結構化索引），元資料支援就是硬需求，FAISS 會擋路。

### 選型決策規則
| 情境 | 選擇 |
|---|---|
| 新手入門 / 小型專案 | **ChromaDB 或 FAISS** — 與 LangChain/LlamaIndex 緊密整合，幾行程式碼可跑 |
| 資料量超過百萬級 | Milvus / Weaviate / Pinecone |
| 需要高並發、即時更新、複雜元資料過濾 | Milvus / Weaviate / Pinecone |
| 效能敏感、中小規模 | Qdrant |
| 完全不想維運 | Pinecone |

### 向量資料庫 vs 傳統資料庫
| 維度 | 向量資料庫 | 傳統資料庫 (RDBMS) |
|---|---|---|
| 查詢類型 | 相似性搜尋（ANN） | 精確匹配（`WHERE age = 25`） |
| 一致性 | 通常為**最終一致性** | **強一致性**（ACID 事務） |
| 資料型態 | 高維向量（數百至數千維） | 結構化欄位 |
| 關係 | **互補** — 傳統庫存業務元資料，向量庫存 AI 產生的向量 | |

## Worked Example
**FAISS 索引建立的內部流程**——書中透過 LangChain 源碼追蹤，展示了分層解耦的設計：

1. **`from_documents`（封裝層）** — 從 `Document` 列表中提取純文字內容 (`page_content`) 與元資料 (`metadata`)，傳給 `from_texts`。

2. **`from_texts`（向量化入口）** — 接收文字列表，執行關鍵第一步：調用 `embedding.embed_documents(texts)` **批次**轉換為向量。完成後把向量與其他資訊傳給內部方法 `__from`。

3. **`__from`（建構索引框架）** — 依指定的距離策略（**預設 L2 歐氏距離**）初始化一個空的 FAISS 索引結構（如 `faiss.IndexFlatL2`）。同時準備 `docstore`（存文件原文）與 `index_to_docstore_id`（連接 FAISS 索引與文件的映射）。最後調用 `__add`。

4. **`__add`（填充資料）** — 三個關鍵操作：
   - **加入向量**：轉為 numpy 陣列，調用 `self.index.add(vector)` 批次加入
   - **儲存文件**：文字與元資料打包成 `Document`，存入 `docstore`
   - **建立映射**：更新 `index_to_docstore_id`，建立 FAISS 內部整數 ID（0, 1, 2...）到文件唯一 ID 的映射

**為什麼這個流程值得理解**：FAISS 只存**向量**，文件原文存在另一個 `docstore` 裡，兩者靠映射表連接。這解釋了為什麼 FAISS 的元資料支援弱——它從架構上就不管元資料，那是外掛的 Python 字典。當你需要「先按元資料過濾再搜尋」時，這個設計就成了瓶頸。

## Key Takeaways
1. 向量資料庫解決的是**規模問題**：暴力線性搜尋在百萬級以上無法接受。
2. **向量庫與傳統資料庫互補**：前者存 AI 向量，後者存業務元資料與結構化資訊。
3. **四類 ANN 索引**：樹（Annoy）、雜湊（LSH）、圖（**HNSW**）、量化（**IVF/PQ**）。
4. **FAISS 是函式庫不是資料庫**：無持久化、單機、元資料弱、並發受限。索引存成本地 `.faiss` + `.pkl` 檔案。
5. **選型分水嶺**：小型專案用 ChromaDB/FAISS；超過百萬級或需高並發/複雜元資料過濾才上 Milvus/Weaviate/Pinecone。
6. 元資料過濾能力是**硬需求**，若檢索流程需要「先過濾後搜尋」，FAISS 會擋路。
