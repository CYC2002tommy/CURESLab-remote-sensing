# Chapter 11: 查詢路由 — 智能調度與檢索策略選擇

## Core Idea
當系統接入多個資料源或具備多種處理能力時，需要一個「智能調度中心」分析查詢並動態選擇處理路徑。路由的本質是**用語義理解替代硬編碼規則**。

## Frameworks Introduced

- **三種路由應用場景**：
  - When to use: 判斷你的系統需不需要路由。
  - How:

| 場景 | 判斷依據 | 範例 |
|---|---|---|
| **資料源路由**（最常見） | 查詢意圖 | 「最新的 iPhone 有什麼功能？」→ 產品文檔向量庫<br>「我上次訂購了什麼？」→ 使用者歷史 SQL 庫（Text-to-SQL）<br>「A 公司和 B 公司的投資關係？」→ 企業知識圖譜 |
| **組件路由** | 問題複雜性（平衡成本與效果） | 簡單 FAQ → 直接向量檢索（快、便宜）<br>複雜操作或需外部 API → 調用 Agent |
| **提示模板路由** | 任務類型 | 數學問題 → 含分步思考的模板<br>程式碼生成 → 專為程式碼優化的模板 |

- **兩種路由實作方法**：
  - How:

| 方法 | 機制 | 延遲 | 靈活性 |
|---|---|---|---|
| **基於 LLM 的意圖識別** | 設計含路由選項的提示詞，LLM 直接對查詢分類並輸出標籤 | 高（一次 LLM 呼叫） | **最靈活** |
| **嵌入相似性路由** | 計算查詢與預設「路由示例語句」的向量相似度 | **低**（無 LLM 呼叫） | 較受限 |

- **LLM 意圖識別的三步實作**（LangChain LCEL）：
  1. **定義分類器** — `classifier_chain` 讀取使用者問題，用 LLM 打上分類標籤（如 `'川菜'`, `'粤菜'`, `'其他'`）
  2. **定義路由分支** — `RunnableBranch` 定義路由規則，像 `if-elif-else`，依 `topic` 欄位選擇執行哪個處理鏈
  3. **組合完整路由鏈** — `full_router_chain` **並行**執行兩個操作（用 `classifier_chain` 產生 `topic`，同時保留原始 `question`），然後把含 `topic` 與 `question` 的字典傳給 `router_branch`

- **嵌入相似性路由的四步實作**：
  1. **定義路由描述並向量化** — 為每個路由寫詳細文字描述，用嵌入模型轉為向量
  2. **定義目標鏈** — 用字典 `route_map` 將路由名稱與鏈對應
  3. **定義路由函數** — `route` 函數接收問題，計算與各路由描述的相似度，選最相似的並調用對應鏈
  4. **組合並調用** — 用 `RunnableLambda` 包裝成可執行的路由鏈

- **三種檢索策略與決策規則**（圖 RAG 場景的具體應用）：
  - How:

| 策略 | 適用查詢 | 機制 |
|---|---|---|
| **傳統混合檢索** | 簡單查詢 | 結合雙層檢索與向量檢索 |
| **圖 RAG 檢索** | 複雜推理查詢 | 基於圖結構進行**多跳推理** |
| **組合檢索策略** | 中等複雜查詢 | 結合傳統檢索與圖 RAG 的優勢，用 **Round-robin 輪詢合併** |

  **決策規則**：
  - 簡單查詢（複雜度 < 0.4）→ 傳統混合檢索
  - 複雜推理查詢（複雜度 > 0.7 **或** 關係密集度 > 0.7）→ 圖 RAG 檢索
  - 中等複雜查詢（0.4 ≤ 複雜度 ≤ 0.7）→ 組合檢索策略

- **Round-robin 輪詢合併** — 融合多路結果的簡單替代方案。
  - When to use: 不想調融合權重時。
  - How: 按固定輪轉順序從不同結果列表交替選擇——第 1 個位置選傳統檢索的第 1 個結果，第 2 個位置選圖 RAG 的第 1 個結果，第 3 個位置選傳統檢索的第 2 個，依此類推。
  - Why it works: 這是一種**公平調度算法**。確保每種檢索策略的結果都能得到公平展示機會，避免某方法因排序靠前而被過度選擇。**實作簡單且穩定，無需調優權重參數，自然保持結果多樣性。**
  - vs RRF：RRF 用倒數排名加權融合；Round-robin 純粹按位置輪轉。後者更簡單但完全不考慮分數。

## Key Concepts
- **LCEL (LangChain Expression Language)** — 用 `|` 管道符號串接組件的宣告式方法。`prompt | llm | parser` 定義「提示→模型→解析器」的順序。LangChain 會在底層自動做並行、非同步與串流優化。
- **`RunnableBranch`** — LCEL 中的條件分支組件。
- **降級分析 (Fallback analysis)** — LLM 分析失敗時，改用基於規則的簡單判斷。
- **`RouterQueryEngine` / `QueryEngineTool`** — LlamaIndex 的路由實作，把資料源或策略包裝成「工具」，用 `Selector`（`LLMSingleSelector` 或更穩定的 `PydanticSingleSelector`）選擇。

## Mental Models
- **路由是「用語義理解替代硬編碼規則」**：if-else 寫不完所有查詢類型，語義匹配可以泛化。
- **路由的價值 = 省下的成本 + 提升的準確率**：把簡單 FAQ 導向便宜路徑，把複雜查詢導向昂貴但有效的路徑。若所有查詢都一樣複雜，路由沒有價值。
- **嵌入路由用延遲換靈活性**：無 LLM 呼叫所以快，但只能做文字相似度匹配，處理不了複雜路由邏輯。
- **必須有降級路徑**：LLM 分析會失敗（超時、格式錯誤、API 故障）。書中明確設計了「基於規則的降級分析」。

## Anti-patterns
- **沒有降級方案就依賴 LLM 路由**：LLM 分析失敗時整個系統會斷。必須有規則基礎的 fallback。
- **對單一資料源的系統上路由**：只有一個地方可去時，路由是純粹的成本。
- **用嵌入相似性路由處理複雜路由邏輯**：它只是文字相似度匹配。LlamaIndex 的設計哲學正是把語義路由融合進 LLM 意圖識別，因為「這種方式更靈活，能處理更複雜的路由邏輯，而不僅僅是文字相似度匹配」。
- **忽略 Round-robin 這個簡單選項**：不是所有融合都需要 RRF 或加權。當你只想要多樣性且不想調參時，輪詢就夠了。

## Worked Example
**智能查詢路由器的四維度分析框架**（書中圖 RAG 專案的實作）。

路由器透過四個維度分析查詢特徵，輸出 `QueryAnalysis` 物件，其中包含 `recommended_strategy`。

**查詢複雜度分級的實際例子**：

| 複雜度 | 查詢範例 | 特徵 |
|---|---|---|
| **簡單** | 「川菜有哪些？」<br>「宮保雞丁怎麼做？」<br>「減肥菜推薦」 | 單一意圖，直接查詢 |
| **中等複雜** | 「家常菜中哪些適合新手製作？」<br>「有什麼菜可以用剩餘的土豆和胡蘿蔔？」 | 有約束條件，但關係不深 |
| **複雜推理** | 「適合糖尿病人吃的低糖川菜有哪些，並且製作時間不超過 30 分鐘？」<br>「如果我只有雞肉和蔬菜，能做什麼菜，最好是不同菜系的？」<br>「哪些菜可以用豆腐替代肉類，並且保持相似的口感？」 | **多重約束 + 需要關係推理** |

**路由執行流程**：
1. LLM 分析查詢，輸出四維度特徵與 `recommended_strategy`
2. 若 LLM 分析失敗 → **降級到規則判斷**（簡單的關鍵詞與長度啟發式）
3. 依複雜度閾值選擇策略：< 0.4 傳統、> 0.7 圖 RAG、之間用組合
4. 記錄路由統計，供後續優化

**組合策略中的 Round-robin**：傳統檢索與圖 RAG 各自回傳結果後，按位置輪流取——傳統[0]、圖RAG[0]、傳統[1]、圖RAG[1]……這避免了複雜的分數融合計算，透過位置輪轉自然實現不同策略結果的均衡分布。

## Key Takeaways
1. 路由的本質是**用語義理解替代硬編碼規則**，三種場景：資料源路由、組件路由、提示模板路由。
2. **LLM 意圖識別最靈活但有延遲**；**嵌入相似性路由延遲低但只能做文字相似度匹配**。
3. **必須設計降級路徑** — LLM 分析失敗時退回規則判斷。
4. 檢索策略決策規則：**複雜度 < 0.4 → 傳統；> 0.7 或關係密集度 > 0.7 → 圖 RAG；之間 → 組合**。
5. **Round-robin 輪詢合併**是 RRF 之外的簡單選項：按位置輪轉，無需調權重，自然保持多樣性。
6. LCEL 的 `|` 管道語法讓路由鏈可讀，且底層自動做並行/非同步/串流優化。
