# Chapter 17: 知識圖譜與 Neo4j — 結構化關係的表示與查詢

## Core Idea
知識圖譜用**三元組（實體）-[關係]->（實體）**結構化描述現實世界。相對關聯式資料庫，圖資料庫的優勢在於**對「關係」的查詢效能**——多層關係遍歷（如「我朋友的朋友」）時效果遠超 RDBMS。

## Frameworks Introduced

- **知識圖譜的兩個核心要素**：
  1. **節點 (Nodes)** — 代表現實世界中的「實體」（人、電影、公司、概念）
  2. **邊 (Edges)** — 代表實體與實體之間的「關係」

  基本結構：**（實體）- [關係] -> （實體）** 的三元組 (Triples)。範例：（餃子）-[導演]->（哪吒2）。

- **Neo4j 資料模型的四個概念**：

| 概念 | 說明 | 類比 |
|---|---|---|
| **節點 (Node)** | 圖中的基本資料單元，表示實體 | 關聯式資料庫中表的一行 |
| **標籤 (Label)** | 為節點分類或打「型別」標記。**一個節點可擁有多個標籤**（如同時是 `:Person` 和 `:Author`） | 表名 |
| **關係 (Relationship)** | 圖資料庫的精髓。**必須有方向、必須有型別**，可擁有屬性 | 外鍵（但更豐富） |
| **屬性 (Property)** | 以鍵值對形式儲存在節點和關係上的詳細資訊 | 欄位 |

- **知識圖譜的經典建構流程**（傳統 NLP 路徑）：
  1. **命名實體識別 (NER)** — 從文本中識別並抽取特定類別的實體。這些實體成為圖譜中的**節點**。
     - 例：「英偉達發布了專為 AI 設計的 Blackwell 晶片」→ 識別出「英偉達」（公司）、「Blackwell」（產品）
  2. **關係抽取 (RE)** — 判斷實體與實體之間存在何種語義關係。這個關係成為連接兩個節點的**邊**。
     - 例：判斷「英偉達」和「Blackwell」之間的關係是「發布」

- **大模型帶來的革新與 GraphRAG**：
  - **LLM 的局限**：完全依賴 LLM 會面臨成本高昂、資料隱私（使用閉源 API 時）、以及**「幻覺」問題**——模型可能編造事實。
  - **微軟提出的 GraphRAG 融合方案**：把知識圖譜作為**可靠、可隨時更新的外部知識庫**，基於圖結構進行**「子圖檢索」**（社群發現、路徑搜尋等），**而非檢索孤立事實**。流程：
    1. 利用模型從問題中識別出**核心實體與約束**
    2. 在圖中檢索與之高度相關的**子圖**（社群/路徑/鄰域），獲得準確且**可解釋**的事實與關係
    3. 將該子圖的結構化資訊作為上下文，連同原始問題輸入 LLM，生成基於證據的答案

- **KBQA（基於知識圖譜的問答）四步流程**：
  1. **意圖識別** — 判斷提問意圖（「我想買一張明天上午的故宮門票」→ 意圖是「票務預訂」）
  2. **槽位填充（實體抽取）** — 抽取關鍵資訊：`景點: 故宮, 時間: 明天上午, 數量: 一張`
  3. **知識查詢** — 用抽取的實體在知識圖譜（或資料庫）中精確查詢
  4. **回覆生成** — 透過預設模板生成自然語言回覆
  - **定位**：雖不如 LLM 靈活，但在機票預訂、酒店查詢、銀行客服等**業務邏輯明確**的場景中，能提供**更可靠和可控**的服務。其**答案的準確性與可解釋性仍具有不可替代的價值**。

## Key Concepts
- **Cypher** — Neo4j 的宣告式圖查詢語言，語法靈感來自 SQL 但針對圖特性優化。
- **`DETACH DELETE`** — 自動刪除指定節點及所有與它直接相連的關係。**官方推薦方式。**
- **`MERGE`** — 「存在則更新，不存在則建立」。配合 `ON CREATE SET` / `ON MATCH SET` 使用。建構知識圖譜時避免重複建立實體的關鍵。
- **`coalesce(property, defaultValue)`** — 檢查屬性是否存在，存在則回傳其值，否則回傳預設值。
- **軟刪除 (Soft delete)** — 生產環境的安全做法：用 `SET` 加上狀態屬性標記為「已刪除」，查詢時加 `WHERE i.is_active = true` 過濾。資料仍保留以備審計或恢復。

## Mental Models
- **圖資料庫的價值在「關係查詢」不在「資料儲存」**：如果你的查詢從不需要多跳遍歷，用 RDBMS 就好。
- **「近朱者赤，近墨者黑」是圖譜應用的核心直覺**：一個實體的風險或屬性，往往與其關聯的其他實體有很強的相關性。這是風險識別、反欺詐應用的理論基礎。
- **GraphRAG 檢索的是「子圖」不是「事實」**：這是它與傳統 RAG 最根本的差異。子圖攜帶關係結構，孤立事實不攜帶。
- **LLM 沒有取代 NER/RE，而是與之融合**：完全依賴 LLM 有成本、隱私、幻覺三個問題。實務上是深度融合的趨勢。

## Anti-patterns
- **直接 `DELETE` 還有關聯關係的節點**：**Neo4j 不允許**，會報錯。必須先刪除關係，或使用 `DETACH DELETE`。
- **生產環境物理刪除資料**：書中明確警告「直接從資料庫中物理刪除（`DELETE`）資料是一種高風險操作」。應採用**軟刪除**。
- **用 `CREATE` 建構知識圖譜的實體**：會產生重複節點。應用 `MERGE`。
- **完全依賴 LLM 做知識抽取**：成本高、隱私風險、會編造事實。
- **對業務邏輯明確的場景硬上 LLM**：機票預訂、銀行客服這類，KBQA 的準確性與可解釋性更適合。

## Reference Tables

### Cypher 核心操作
| 操作 | 語法 | 要點 |
|---|---|---|
| **建立節點** | `CREATE (變數:標籤 {屬性: 值})` | 變數可省略（後續不需引用時） |
| **建立關係** | `-[變數:型別 {屬性}]->` | `()` 表節點，`[]` 表關係。**必須有方向和型別** |
| **查詢** | `MATCH (n:Label {prop: val}) RETURN n` | 用 `LIMIT` 避免資料量過大卡住瀏覽器 |
| **條件查詢** | `MATCH (n) WHERE n.name IN [...] RETURN n` | 支援 `AND` / `OR` 複合條件 |
| **關聯查詢** | `MATCH (d:Dish)-[:包含]->(i:Ingredient)` | 圖資料庫最強大之處 |
| **聚合** | `collect(i.name)` | 把多個結果收集到列表 |
| **更新屬性** | `MATCH ... SET n.prop = val` | 必須配合 `MATCH` |
| **插入或更新** | `MERGE ... ON CREATE SET ... ON MATCH SET ...` | **建構圖譜時避免重複的關鍵** |
| **移除屬性** | `REMOVE n.prop` | 只移除屬性不刪節點 |
| **刪除節點** | `MATCH (n) DETACH DELETE n` | **推薦方式**，自動處理關係 |
| **排序** | `ORDER BY i.name ASC` | 預設升序 |

### 知識圖譜的三類工業應用
| 應用類別 | 場景 | 核心邏輯 |
|---|---|---|
| **風險識別與網路分析** | 犯罪網路偵查、信用卡反欺詐 | 分析網路中的核心人物（連接數最多的節點）與資金流向；識別共享同一電話/地址的欺詐團夥 |
| **智慧診斷與運維** | 工業設備運維、醫療輔助診斷 | 把「故障現象」「故障原因」「解決方案」「所需零件」構成圖譜，依上報現象推理定位 |
| **特定領域聊天機器人 (KBQA)** | 機票預訂、酒店查詢、銀行客服 | 意圖識別 → 槽位填充 → 知識查詢 → 回覆生成 |

## Worked Example
**軟刪除 vs 硬刪除**——生產環境的正確做法。

**錯誤示範**：
```cypher
// 如果'大蒜'還有關係連著，這條語句會報錯
MATCH (i:Ingredient {name:'大蒜'})
DELETE i;
```
Neo4j 不允許刪除還有關聯關係的節點。

**正確做法 1**（先刪關係再刪節點）：
```cypher
MATCH (i:Ingredient {name:'大蒜'})-[r]-()   // 匹配與'大蒜'相連的任意關係
DELETE r, i;                                 // 先刪關係 r，再刪節點 i
```

**正確做法 2**（官方推薦）：
```cypher
MATCH (i:Ingredient {name:'大蒜'})
DETACH DELETE i;
```

**生產環境的最佳做法——軟刪除**：
```cypher
// 將"木耳"標記為不活躍，而非真的刪除
MATCH (i:Ingredient {name:'木耳'})
SET i.is_active = false;
```
後續查詢只需加上 `WHERE i.is_active = true` 過濾。**資料仍保留在資料庫中，以備審計或恢復。**

**書中的警告原文**：「刪除操作是高風險行為，尤其是在生產環境中。執行前請務必確認操作對象和範圍，並做好資料備份。」

**為什麼這個例子重要**：知識圖譜的實體通常被大量關係引用。硬刪除一個節點會**級聯破壞**所有引用它的關係，而這些關係可能是其他推理路徑的必經之路。軟刪除保留了圖的完整性。

## Key Takeaways
1. 知識圖譜 = **（實體）-[關係]->（實體）** 三元組。節點是實體，邊是關係。
2. **圖資料庫的優勢在多層關係遍歷**——「我朋友的朋友」這類查詢遠超 RDBMS。若不需要多跳，用 RDBMS 即可。
3. **Neo4j 四概念**：節點、標籤（可多個）、關係（**必須有方向和型別**）、屬性。
4. **經典建構流程 = NER（抽實體→節點）+ RE（抽關係→邊）**。LLM 沒有取代它們，而是融合。
5. **GraphRAG 檢索「子圖」而非「孤立事實」**——子圖攜帶關係結構，這是可解釋性的來源。
6. **建構圖譜用 `MERGE` 不用 `CREATE`**（避免重複）；**刪除用 `DETACH DELETE`**（Neo4j 不允許刪除有關係的節點）；**生產環境用軟刪除**。
7. **KBQA 在業務邏輯明確的場景中不可替代**——準確性與可解釋性勝過 LLM 的靈活性。
